# Phase 4: EU AI Act Audit Report: Interview Prep Report

**System owner:** Julia Antunes · **Auditor:** Ayhan Demir · **Date:** 17 Nov 2026
**Basis:** Julia's system brief, my annotations, and the assumptions in the clarifying questions log · **Scope:** EU AI Act only (Regulation (EU) 2024/1689 as amended by Regulation (EU) 2026/1744)

## 1. System summary

Interview Prep Report is an n8n workflow that helps a job seeker get ready for an interview. The user enters a company name and a job description and uploads a CV, a GitHub profile or both. The workflow researches the company and its recent news, compares the job requirements with the person's experience, and uses an OpenAI model to write an HTML report covering what to highlight, possible skill gaps and five likely interview questions. It produces no score and no decision, is meant only for the job seeker's own use, and leaves the user to check the report before relying on it.

## 2. Risk classification

**First-pass tier: limited risk** (transparency duties under Art. 50, plus Art. 4 AI literacy).

- **Not prohibited:** no practice in Art. 5 applies.
- **Not high-risk on its stated purpose:** comparing a CV with a job description is the same activity Annex III point 4(a) describes ("evaluate candidates"), but the intended purpose is self-preparation by the candidate, with no score or selection. Intended purpose decides the classification (Art. 3(12)).
- **Uncertainty:** the brief states the purpose well but describes no control that keeps the system there. If recruiters or employers used it on applicants' CVs, it would be high-risk, and because a skill-gap analysis of a named person is profiling, the Art. 6(3) exception could not be used.

## 4. Compliance findings

**Finding 1: AI disclosure to the user (Art. 50(1) and 50(5))**
**Severity:** Significant
**Description:** The provider must make sure people know they are dealing with an AI system, clearly and at the latest at the first interaction, unless it is obvious. The brief describes the report but not any notice that it is AI-generated.
**Recommended action:** Add a short line on the input page and at the top of the report: "This report is generated by AI and can be wrong. Check every claim and link before you use it."
**Escalation needed?** No.

**Finding 2: Machine-readable marking of the report (Art. 50(2))**
**Severity:** Significant
**Description:** Systems that generate text must mark their outputs in a machine-readable format so they are detectable as AI-generated. The HTML report has no marking described.
**Recommended action:** Add a machine-readable marker in the HTML (for example a meta tag stating AI generation, the model and the date) and follow the Commission's Code of Practice on Transparency of AI-Generated Content (June 2026) for the method.
**Escalation needed?** No, unless the report will be widely distributed; then confirm the technique with legal counsel.

**Finding 3: No safeguard against use by employers or recruiters (Annex III 4(a), Art. 25(1)(c))**
**Severity:** Significant
**Description:** The brief rightly says the system is "not a hiring tool", but nothing stops a recruiter or coach from uploading other people's CVs. That use would turn the same workflow into a high-risk candidate-evaluation system, with no Art. 6(3) way out because it profiles people.
**Recommended action:** (1) State the intended purpose and the prohibited use ("not for assessing or selecting candidates") on the input page and in short terms of use. (2) Add a checkbox: "This is my own CV / profile." (3) Do not offer exports or sharing aimed at employers.
**Escalation needed?** Yes, to legal counsel, if the tool is ever offered to organisations (careers services, agencies, employers).

**Finding 4: Non-high-risk assessment not documented**
**Severity:** Minor
**Description:** The brief contains the right reasoning (no score, no decision, candidate's own use), but it is not recorded as a classification decision. Art. 6(4) requires this only if a provider relies on the Art. 6(3) exception, which is not the case here, but a short record protects the provider if the use changes.
**Recommended action:** Keep a one-page note in the repository: intended purpose, why Annex III 4(a) does not apply, and what would change the answer.
**Escalation needed?** No.

**Finding 5: AI literacy (Art. 4)**
**Severity:** Minor
**Description:** Providers must take measures to support the AI literacy of the people who operate the system on their behalf. For a solo provider this is light, but it grows if others help run or offer the tool.
**Recommended action:** Add a short "Limits of this report" section to the README and the report (what the model can get wrong, why links must be checked).
**Escalation needed?** No.

**Finding 6: Information from the model provider (Art. 53(1)(b))**
**Severity:** Minor
**Description:** As a downstream provider, Julia relies on OpenAI's model. OpenAI must give downstream providers information on the model's capabilities and limits.
**Recommended action:** Keep a link to OpenAI's model documentation and usage policies in the repository, and record which model version the workflow uses.
**Escalation needed?** No.

## 5. Overall recommendation

**Proceed with conditions.** There are no blocking findings: the system is not a prohibited practice and, on its stated purpose, not high-risk. Before it is offered to other people, three conditions should be met: (1) a visible AI notice on the input page and the report (Finding 1); (2) a machine-readable AI marker in the HTML report (Finding 2); and (3) the intended purpose and the ban on use for assessing candidates stated to users, with an own-CV confirmation (Finding 3). The minor findings can follow after launch. The classification should be reviewed again if the tool is offered to any organisation.

## 6. What this report is not

This report is not a legal opinion, not a conformity assessment and not a certification. It is a first-pass review based only on the system brief, for a course exercise. Its conclusions should be verified with legal counsel before any placement on the EU market.



## 7. Joint closing note

Both audits agreed the system is not high-risk and found the same two core risks: Article 50 transparency and the line between process advice and employment use. That shows we read the regulation the same way. The differences came from what each of us knew. As the builder, Ayhan treated the confidence scores and his own accountability as settled because he had tested them and knew who owned them. Reading only the page, Julia rightly flagged both as unvalidated and undocumented. Auditing our own work, we fill gaps in the brief from memory. Auditing someone else’s turns every unstated assumption into a question or a finding, so the external audit was stricter on evidence and ownership, while the self-audit was sharper on the specific AI Act duties the builder knew the system triggers.
