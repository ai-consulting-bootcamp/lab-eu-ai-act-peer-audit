# Phase 1 — Read and annotate

## System summary

Board Game Concierge is a Telegram-based AI assistant designed to help users play and choose board games. Users can ask questions about game rules, ask follow-up questions, receive strategy tips, and request recommendations based on criteria such as player count, playtime, and complexity.

Telegram is the primary user interface. n8n orchestrates the interaction and calls a FastAPI backend. The system uses OpenAI for conversational synthesis, Pinecone to retrieve imported rulebook content, local structured data for recommendations, and external search providers for some strategy queries.

The intended use is recreational board-game assistance. Nothing in the reviewed system description indicates use in employment, education, essential services, law enforcement, migration, biometric identification, justice, or another Annex III high-risk domain.

## Risk-relevant annotations

### Elements affecting classification
- Direct interaction between an AI system and natural persons through Telegram.
- Generative AI produces explanations, recommendations, and strategy responses.
- Intended use is recreational and low-consequence.

### Elements initially unclear
- Whether users were explicitly informed they were interacting with AI.
- Whether the intended purpose could extend beyond recreational use.
- Which parts of the system process user-derived information.

### Elements triggering specific obligations
- Direct conversational interaction triggers the transparency analysis under Article 50(1).

# Phase 3 — Clarifying questions log

## Question 1 — AI transparency

**What I needed to know:**  
When users first interact with the Telegram bot, are they explicitly told that responses are generated by or with AI?

**Why it matters:**  
This determines whether Article 50(1) is already addressed.

**My provisional assumption:**  
I assumed disclosure was not evidenced because I could not find it in the project documentation.

**Mudit's answer:**  
No. A small subtext suggesting that responses were automatically generated through n8n had existed but was removed before the demo.

**Updated conclusion:**  
The transparency obligation is currently a genuine gap rather than merely an undocumented safeguard.

## Question 2 — Personal-data flow

**What I needed to know:**  
Which Telegram information passes through the system?

**Why it matters:**  
Although primarily relevant to GDPR, this helps identify the system's actual interaction model and third-party dependencies.

**My provisional assumption:**  
Message content and some routing identifier were probably processed.

**Mudit's answer:**  
The system processes message text, follow-up questions, Telegram user ID/chat ID, username/display name if present, user-stated game preferences or constraints, and short-lived conversation context/pending intent.

**Updated conclusion:**  
The system processes more user-derived information than was explicit in the original documentation, creating parallel GDPR obligations that should be addressed separately.

## Question 3 — Pinecone and external providers

**What I needed to know:**  
Do raw user messages, identifiers, or conversation history enter Pinecone or the external search providers?

**My provisional assumption:**  
Pinecone stores the documented rulebook chunks only.

**Mudit's answer:**  
Not directly. Messages are processed to identify the core message and keywords, which are then sent as query parameters to external APIs.

**Updated conclusion:**  
My assumption that Pinecone primarily stores rulebook material was correct. External search services receive transformed user-derived queries rather than the full raw conversation.

## Question 4 — Storage

**What I needed to know:**  
Is conversation context persisted anywhere beyond the active session?

**My provisional assumption:**  
Application session state is transient/in-memory, while vendor-side logging and retention remain unknown.

**Mudit's answer:**  
Conversation context is in-memory only for the active session.

**Updated conclusion:**  
Application-level conversation persistence appears limited. Vendor-side retention still requires separate verification under GDPR.

## Question 5 — Intended purpose

**What I needed to know:**  
Is the intended use strictly recreational, or could the product be used in more consequential contexts?

**My provisional assumption:**  
Recreational use only.

**Updated conclusion:**  
Nothing in Mudit's clarification contradicts the recreational intended purpose, so the risk-tier classification remains unchanged.

# Phase 4 — Audit report

## Section 1 — System summary

Board Game Concierge is an AI-powered Telegram assistant providing board-game rules explanations, follow-up answers, strategy information, and recommendations. It combines OpenAI-based conversational generation with retrieval from a Pinecone rulebook knowledge base, local recommendation data, and external search APIs. User interactions are orchestrated through n8n and a FastAPI backend. Its intended purpose is recreational assistance rather than consequential decision-making.

## Section 2 — Risk classification

**Final classification: Limited risk / transparency**

There is no evidence of an Article 5 prohibited use or Annex III high-risk use.

Article 50(1), however, is relevant because the system is designed to interact directly with natural persons.

After clarification from Mudit, the transparency gap is confirmed: users are currently not explicitly informed that responses are AI-generated or AI-assisted.

## Section 3 — Role map

| Actor | Provisional role | Key implication |
|---|---|---|
| Board Game Concierge project owner/operator | Provider of the final AI system if the system is developed and put into service under their name | Responsible for applicable provider obligations and final-system transparency. |
| Telegram users | Recipients/users interacting with the system | Should receive the applicable AI-interaction transparency. |
| OpenAI | Upstream third-party AI/model service | Its regulatory role is distinct from the project operator's responsibility for the final user experience. |
| Telegram | Third-party communication platform | Mainly relevant to parallel privacy and data-flow obligations. |
| n8n | Workflow/orchestration service | Mainly relevant to parallel privacy and data-flow obligations. |
| Pinecone | Vector database / infrastructure service | Mainly relevant to parallel privacy and data-flow obligations. |
| SerpApi / Serper / Tavily | Third-party search services | Mainly relevant to parallel privacy and data-flow obligations. |

Because the system is not classified as high-risk, the 11 high-risk provider obligations are not applied as a mandatory checklist.

## Section 4 — Compliance findings

### Finding 1 — Article 50 AI interaction disclosure

**Severity:** Significant

**Description:**  
Board Game Concierge directly interacts with natural persons through Telegram. Mudit confirmed that the application currently does not explicitly tell users that responses are generated using AI.

**Recommended action:**  
Add a clear disclosure before or at the first interaction, for example: **"I'm an AI-powered Board Game Concierge."** The implementation should also be documented so that compliance can be evidenced.

**Escalation needed?**  
No. This can be addressed directly through product/UI implementation.

### Finding 2 — Transparency evidence

**Severity:** Minor

**Description:**  
The architecture documents AI use, but there is currently no documented evidence showing where the Article 50 disclosure appears in the actual user journey.

**Recommended action:**  
Add the transparency decision and implementation location to the README or compliance documentation.

**Escalation needed?**  
No.

### Finding 3 — Parallel GDPR governance

**Severity:** Significant

**Description:**  
The clarification revealed that Telegram user IDs/chat IDs, usernames/display names when present, message text, preferences, and short-lived conversational state are processed.

These do not change the AI Act classification, but they create a substantive parallel GDPR compliance layer.

**Recommended action:**  
Complete the GDPR data map, vendor role analysis, retention assessment, and privacy notice.

**Escalation needed?**  
Yes — privacy/legal review before broader deployment.

### Finding 4 — Intended-purpose boundary

**Severity:** Minor

**Description:**  
The limited-risk classification relies on the product remaining a recreational board-game assistant.

**Recommended action:**  
Record the intended purpose and perform a fresh classification if the product is materially repurposed.

**Escalation needed?**  
No.

## Section 5 — Overall recommendation

### PROCEED WITH CONDITIONS

Board Game Concierge is appropriately classified as **limited risk / transparency**. Both the independent audit and builder self-audit reached the same conclusion.

The primary AI Act remediation is straightforward but material: reinstate a clear AI disclosure in the Telegram user journey.

The identified GDPR issues should also be addressed before broader deployment but do not change the AI Act risk classification.

## Section 6 — What this report is not

This report is not a legal opinion, conformity assessment, or certification. Its conclusions should be verified with qualified legal counsel before being relied upon for EU market placement.

# Phase 5 — Debrief

## 1. Auditor presents

My independent audit classified Board Game Concierge as **limited risk / transparency** because the system does not fall within Article 5 or an Annex III high-risk area, but directly interacts with users and therefore engages Article 50(1).

My main finding was that the available documentation did not demonstrate an AI-interaction disclosure.

## 2. Builder responds

Mudit confirmed that there is currently no AI disclosure. A small subtext had previously suggested that responses were automatically generated through n8n, but it was removed before the demo.

He also clarified that the system processes Telegram message text, user/chat IDs, usernames/display names when present, preferences, and short-lived conversational context.

## 3. Compare classifications

**Auditor:** Limited risk / transparency.  
**Builder:** Limited risk / transparency obligation under Article 50.

**Result: Full agreement.**

The independent audit and self-audit reached the same regulatory classification.

## 4. Compare gap lists

Mudit's self-audit identified:
- No AI disclosure.
- No privacy notice.
- No retention schedule.
- No RoPA.
- No DPA evidence.
- No documented deletion workflow.
- No data-subject-rights workflow.
- No incident-response process.

My external AI Act audit concentrated more strongly on proving the Article 50 disclosure in the actual user journey and distinguishing AI Act obligations from parallel GDPR vendor/data-flow issues.

Mudit also highlighted areas where my initial external audit could not be conclusive:
- Exact vendor payloads.
- n8n execution-history retention.
- Potential vendor reuse of prompts.
- Undocumented FastAPI processing.

## 5. Joint closing note

The debrief showed that auditing your own system gives you stronger implementation context, while an external audit is more likely to challenge what is actually evidenced in the documentation. In this case we reached the same AI Act classification, but the independent review made the missing Article 50 disclosure especially visible because it could not rely on the builder's knowledge of how the interface was intended to work.

---

# Reinforce

The review showed that technical intent and compliance evidence are not the same thing. A builder may know that a system is low-risk and recreational, but an external reviewer can only rely on what is documented and visible in the product.

The missing AI disclosure is a good example: the product had previously contained a hint that responses were automatically generated, but because that disclosure had been removed, an auditor reviewing the live user experience would correctly treat transparency as a gap.
